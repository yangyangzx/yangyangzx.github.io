P0 反推口径
planner.js		 「请求 2R」实际只达成 1.78R：getTPUnits() 只在 _lastCalc 存在时返回口径，而 calcReverseTP / calcReverseSL / autoCalcMultiTP 三条路径各自静默 fallback 到 stopDistance × rr 纯毛利解。计算结果一旦失效（改过参数还没点「计算仓位」），目标价就按纯毛利回填——而 2R 闸门与结果卡片按含费净判，同一份参数两个结论。

同时发现两处同源分叉：updateMultiTP 在 calc 为 null 时 f 恒为 0，各行显示的是纯毛利 RR，而 autoCalcMultiTP 回填的是含费解；且原实现乘 origPosSize，calc 为 null 时它为 0，0/0 直接显示成 0.00R。		 getTPUnits() 在计算结果不可用时退回表单输入（入场价/止损价/方向/费率），费率与 calculator.js 同源——未填时按订单类型回落 0.08%/0.04%。三条反推路径删除纯毛利兜底，口径拿不到时明说「无法按含费口径反推」而不写错值。calcReverseTP/SL 不再自行重读一遍 calc/表单（原先会出现「方向校验用表单方向、求解用 calc 方向」的错位），全部只认 u。updateMultiTP 费率改从 getTPUnits() 取；RR 是比值、与仓位规模无关，故改用单位净值相除，删掉 origPosSize/riskAmt。

实测（ep 50000 / sl 49000 / 费率 0.08%）：unitLoss = 0.02 + 0.0008×1.98 = 0.021584；请求 2R 含费解 tp = 52240.19（纯毛利 52000，净 RR 仅 1.78R）；tp 52000 反推止损 sd = 879.90 vs 纯毛利 1000——含费更紧，因为费用同时压缩分子（净毛利）并膨胀分母（净止损）。四组残缺参数形态（表单全填 / 未填费率回落 0.08% / 表单未填止损退回 calc / 费率按 0）与无口径路径全部断言，含净 RR 精确等于 2（容差 1e-6，价格按 toFixed(5) 量化后残差实测 6.54e-9，1e-9 会假失败）。
P1 部分平仓编辑

P1 0 条候选仍可覆盖提交
settings.js		 本轮 P2「导入流水线合并」引入的回归：导入 0 条有效记录时仍能走完覆盖提交流程，把全部历史清空。

两个真实触发面：① 去重把整批丢弃——用户把自己导出的那份 CSV 再导入一遍，双键去重（本轮 P2 修的正是这个）判全部重复，report.candidates.length = 0；② 解析阶段全部落空——文件里表头列数与数据行不一致，行被整行跳过。

两者在 _confirmImportThenCommit 的覆盖分支里都没有 candidates.length === 0 的分支：只要 existing > 0 就照样弹确认框，文案诚实地写着「将用文件中的 0 条记录覆盖现有 N 条日志」，用户一点就 _commitImportedLogs([]) 把全部历史清空，还回一条 「已导入 0 条日志」的 success 提示——数据已丢，提示还说是成功的。

回归来源：HEAD~1 的 parseCSVImport 不做任何去重，重复导入自己导出的文件会产生 N 条候选，不会走到 0；本轮双键去重修好「重复导入产生重复记录」的同时，把这个场景变成 0 候选。修好 A 时把 B 的边界打穿，属于典型的「修一个洞时把相邻洞连起来」。

实测：表头 6 列 + 唯一数据行 3 列 → 确认框文案确为「将用文件中的 0 条记录覆盖现有 1 条日志」，确认前后 logs.length 由 1 变 0。		 在 _confirmImportThenCommit 入口加 0 候选护栏：直接改弹纯告知框「没有可导入的记录」并返回，不进任何提交路径。两种模式一并拦下——追加模式提交空数组虽无害，但会给「成功导入 0 条」的误导提示。解析阶段告警照旧跟着提示框显示，不丢信息。

实测（新增 14 条断言，第 26 组）：重复导入去重为 0 时覆盖/追加两条路径都只出告知框、logs 不动、无成功提示；空文件覆盖同样拦下；正常 1 条记录时覆盖确认框与追加确认框照常弹出（护栏没把正常路径关掉）；解析告警出现在告知框文案里。端到端另验：合法 CSV（1 行）走完整 parseCSVImport 流程后 logs 由 1 变 1 且提示「已导入 1 条日志」。

需你过目：导入结果 0 条记录时不再弹「覆盖导入」按钮，只弹一个说明框。这是刻意的——一个不可能带来任何新增数据的「覆盖」操作，没有存在的必要。
