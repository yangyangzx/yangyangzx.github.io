settings.js		 同一份文件内部的重复记录被静默丢掉，不报任何错误：v5.6.9 的「导入流水线合并 + 双键去重」把去重范围建成了 existing 集合，而候选互相之间也在比对——每条候选都往 existing 里写了自己的指纹，后到的相同候选被整条丢弃。

真正的杀伤在分批平仓：3 笔分批共用同一个 groupId、同一个 now 时间戳，且 saveSplit 把每一笔的 closeType / closePrice / rMultiple / pnlAmount 都设成空（开仓时确实还没平仓），而 _logFingerprint 只有 7 个字段且不含这些——等分的分批在去 id 指纹下逐字相同。唯一能区分批次的是 groupLabel（'主'/'第N笔'），而它不在 CSV_FIELD_MAP 里，导出时就被丢掉了。

复现：3 笔等分分批（各 33.33%）导出 → 清空 ID 列 → 重新导入 → logs 由 3 变 1，errors = 0、deduped = 0、无任何提示。带着 id 列导入则正常。

关键取舍：内容完全相同的两条记录，与「同一份文件被重复导入两次」在数学上无法区分（无 ID 列时两者都是无 ID 的全同内容）。判重必然二选一，而误伤的代价是静默丢掉真实交易——比「多出一条重复记录」严重得多。		 去重只针对现有日志，同一次导入内部不再互相比对：删掉循环里那两行 existing.add(...)，候选一律入列。真实分批全部保留，「重复导入同一份文件」的判据由与现有日志的比对承担、不受影响。

实测：3 笔等分分批在「带 id / 去 id / 去 id + 去 groupId」三种形态下都全保留；exportCSV 产物清空 ID 列后重新导入仍是 3 条、errors = 0。已知残留：同一次导入里两条真正一模一样（连 id 都相同）的记录会双双保留——这是无外部身份可凭时的必然结果，已在 settings.js 注释里写明。

另改一处探针口径：v5.6.9 起 0 条候选改弹纯告知框而非静默返回，对抗探针里断言「不弹任何框」的 oracle 已过时（数据无损那半断言仍然成立）。已改成断言「没走覆盖路径（不含『不可恢复』）且现有日志无损」。
P1 分批平仓越界
modals.js		 已平 130% 仍能保存成功：编辑分批比例时只校验增量本身在 (0, 100) 内，没校验累计。「原始仓位」口径下增量本身就是占原始仓位的比例，与已平部分相加可以超过 100%。

复现：已平 50% 时输入 80 → 保存成功，得到 closes=[50,80]（sum = 130）、closedRatio 被 clamp 到 100、positionSize 归 0 而 closeType 仍是 partialTP。

后果比一个负数敞口更隐蔽：记录被判成全额平仓（closedRatio = 100），而 closeType 还是分批中间态——仪表盘不会把它当成已平，但账面上的剩余敞口已经消失，权益曲线少算一段风险。同时打破 sum(closes[].ratio) === closedRatio 不变量（130 ≠ 100），这个不变量是 v5.6.1 以来整条分批簿记链的信任基础。

对照：「剩余仓位」口径代数上不会越界——cumBefore + partialRatio × fracBefore = 100 − fracBefore × (100 − partialRatio) < 100，恒成立。		 在增量校验之后补一条累计校验：cumClosedBeforeEvt + deltaOriginal > 100 + 1e-9 即拒绝并 abortSave，回滚整条记录。两种口径统一校验而非只对 'initial' 加——当前只有 'initial' 会触发，但两种口径各写一遍判断条件容易在后续改动时再分叉。

实测：越界输入被拒后 closedRatio / positionSize / closes 三者都不动、不变量成立、toast 文案标出「之前已平 50.00%、本笔 80.00%、超出 30.00%」；同时断言不越界的正常路径没被一起关掉（已平 50、输入 10 → closedRatio = 60、positionSize = 400）。注意这里改的是最后一条事件，编辑是「替换」而不是「叠加」：增量 10 是原始口径下的替换值，与前一条 50 相加得 60，不是 75 + 10。
P2 止损移动幂等
utils.js		 幂等判据比错了对象：recordStopMove 拿新价与 stopHistory 末条比，而末条只反映本函数自己写过的点。用户用编辑弹窗直改 item.stopLoss（emStopLoss 不写 stopHistory）后，两者就会分叉。

分叉之后再移动止损是一次真实变化，按末条比较会把它判成「无需记录」并返回 skipped——stopHistory 停在旧值，item.stopLoss 已经改了，两者从此长期不一致。而仪表盘持仓监控与「止损 vs 强平」距离读的是 stopLoss，复盘页读的是时间线：同一笔交易两套止损距离。		 改与 item.stopLoss 比较，只在它缺失或无效时才退回时间线末条（例如旧数据只有时间线没有 stopLoss）。判据从「与上一条记录比」变成「与当前生效值比」，符合幂等本意。

实测：分叉后移动止损被正确记录；同价时仍然拒绝（判据变了不等于把拒绝能力弄丢了）；stopLoss 被回写；stopLoss 缺失时退回末条仍按老语义工作。
P2 反推止损
planner.js		 反推止损的主流程走不通：calcReverseSL 的未知量就是止损，但入口复用的是 getTPUnits()，而它要求 sd > 0 才返回口径——止损没填时直接 return null，于是「已知入场价 + 目标价 + 期望 RR，反推止损」这条最典型的路径在拿不到口径。

更糟的是外层 getCalcDirty() 闸门把这条路径藏住了：填入场价 + 目标价会触发 input → markCalculationDirty() 标脏，点反推时被闸门挡下并提示「请先点『计算仓位』」，但那时根本还没点过「计算仓位」。真实用户的可见症状因此被掩盖，只在探针里显式 setCalcDirty(false) 才走到 getTPUnits。

另一个小错：报错文案固定写「请先填写入场价」，而入场价已填（只是方向无效）时指错了字段。		 getTPUnits(requireStop) 加一个开关：requireStop = false 时缺失止损不再返回 null，而是把 unitStop / unitLoss 置成 null——不冒充「仅费用」的伪止损（那样未来调用方容易误用成「无风险成本」），且对 requireStop 路径零影响（NaN 与 0 都会走原来的 null 分支）。同时把 sd 的 NaN 归一成 0，免得调用方拿到 NaN。

报错改按真实缺失字段提示：入场价缺失 vs 方向无效。

实测：getTPUnits(false) 在 sd === 0 时仍返回完整口径且 unitStop / unitLoss === null；反推止损产出有效止损且含费净 RR 精确等于 2（容差 1e-6）；含费口径下反推的止损更紧而非更宽（费用同时压缩净毛利、膨胀净止损，与 v5.6.9 的结论一致）；方向无效与入场价缺失各报自己的文案。未改动：getCalcDirty() 闸门本身仍挡在反推入口（见「遗留与未改动」）。
P2 编辑回滚
modals.js		 浅回滚删不掉本次编辑新增的键：abortSave 用 Object.assign(item, beforeEdit) 回滚，而 Object.assign 只会覆盖已存在的键、删不掉 beforeEdit 里没有的键。

触发链：新建日志（saveLog 不写 closes / closedRatio / closeTime / initial*）→ 在编辑弹窗里把平仓类型选成「分批」并填了比例 → syncCloseBookkeeping 写入那一整套键 → 此后任何校验失败 → 浅回滚后 closeType 已回滚成空串、isClosedTrade 判「未平仓」，却带着 closes / closedRatio = 50 / closeTime——全额在仓的持仓同时挂着已平簿记和平仓时间戳。

而且这个残留永远清不掉：syncCloseBookkeeping 在 v5.6.9 加的空值护栏正是「closeType 为空即不动簿记」，所以下一次编辑只要不选类型，残留就一直留着。两条护栏各挡各的，合起来把 bug 锁死了。		 先删掉快照里不存在的键再覆盖：Object.keys(item).forEach(k => { if (!(k in beforeEdit)) delete item[k]; })。这样回滚是真正的「回到编辑前」，包括本次新增的所有键。

实测：新建日志 → 选分批填 50% → 触发校验失败后，closes / closedRatio / closeTime 三个键均不存在（不是被清成 0 或空数组）；其它被新增的字段同样不残留；closeType 回到空串；仓位未被削减；仍判「未平仓」。同时断言空值护栏没把这个正常路径一起关掉。

触发链：下拉有 <option value="">—</option>，saveEditLog 原样赋进 item.closeType；closeType 为空不是分批类型，于是 syncCloseBookkeeping 走「非分批收尾」分支，执行 closedRatio = 100 与 if (!wasFullyClosed) item.closes = []；而 isClosedTrade 首行 !item.closeType 直接判「未平仓」。三处合起来就是「closedRatio=100 + 未平仓 + 剩余敞口仍在」的悬空记录，CSV 导出显示 100% 已平，分批明细全部丢失，而且 partialRatio 被 delete 掉。该分支是 v5.6.1 引入的（当时修的是 closedRatio 该置 100 而非 0），空值路径一直没护栏。		 护栏放在权威实现 utils.syncCloseBookkeeping 开头：!closeType 或非字符串时直接返回，不做任何簿记——这样任何调用方（编辑弹窗、分批保存、confirmClose）都安全，而不是只堵 modals.js 这一处。放在权威处还有一个好处：能直接单测。

实测（新增 7 条断言，第 13 组）：空值在「从未平仓记录」「已部分平仓 50% 记录」「closeType 为 undefined」三种形态下都不动 closedRatio / closes / partialRatio；同时断言正常路径没被护栏一起关掉（partialTP 收尾成 manualWin 仍把 closedRatio 置 100 并删除 partialRatio）。

P1 0 条候选仍可覆盖提交
settings.js		 本轮 P2「导入流水线合并」引入的回归：导入 0 条有效记录时仍能走完覆盖提交流程，把全部历史清空。

两个真实触发面：① 去重把整批丢弃——用户把自己导出的那份 CSV 再导入一遍，双键去重（本轮 P2 修的正是这个）判全部重复，report.candidates.length = 0；② 解析阶段全部落空——文件里表头列数与数据行不一致，行被整行跳过。

两者在 _confirmImportThenCommit 的覆盖分支里都没有 candidates.length === 0 的分支：只要 existing > 0 就照样弹确认框，文案诚实地写着「将用文件中的 0 条记录覆盖现有 N 条日志」，用户一点就 _commitImportedLogs([]) 把全部历史清空，还回一条 「已导入 0 条日志」的 success 提示——数据已丢，提示还说是成功的。

回归来源：HEAD~1 的 parseCSVImport 不做任何去重，重复导入自己导出的文件会产生 N 条候选，不会走到 0；本轮双键去重修好「重复导入产生重复记录」的同时，把这个场景变成 0 候选。修好 A 时把 B 的边界打穿，属于典型的「修一个洞时把相邻洞连起来」。

实测：表头 6 列 + 唯一数据行 3 列 → 确认框文案确为「将用文件中的 0 条记录覆盖现有 1 条日志」，确认前后 logs.length 由 1 变 0。		 在 _confirmImportThenCommit 入口加 0 候选护栏：直接改弹纯告知框「没有可导入的记录」并返回，不进任何提交路径。两种模式一并拦下——追加模式提交空数组虽无害，但会给「成功导入 0 条」的误导提示。解析阶段告警照旧跟着提示框显示，不丢信息。

实测（新增 14 条断言，第 26 组）：重复导入去重为 0 时覆盖/追加两条路径都只出告知框、logs 不动、无成功提示；空文件覆盖同样拦下；正常 1 条记录时覆盖确认框与追加确认框照常弹出（护栏没把正常路径关掉）；解析告警出现在告知框文案里。端到端另验：合法 CSV（1 行）走完整 parseCSVImport 流程后 logs 由 1 变 1 且提示「已导入 1 条日志」。

需你过目：导入结果 0 条记录时不再弹「覆盖导入」按钮，只弹一个说明框。这是刻意的——一个不可能带来任何新增数据的「覆盖」操作，没有存在的必要。
